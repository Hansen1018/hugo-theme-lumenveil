{{- /* main-sections.html — the single resolution of site.Params.mainSections. Returns a lowercased, whitespace-trimmed slice: the configured value, or (slice "archives" "posts") when the configured value is EMPTY. "empty", not "none" — those are different cases and only one of them reaches the fallback branch. Measured on 0.166.0: mainSections omitted, content/posts/ only -> site.Params.mainSections == [posts] Hugo's built-in default -> `not $mainSections` is FALSE, branch not taken mainSections = [], same content -> site.Params.mainSections == [] -> branch taken, returns (slice "archives" "posts") Hugo fills the default in whenever the site has any top-level section, so OMITTING the key does not reach the fallback — an earlier version of this comment said "when the site configures none", which is wrong and invited reading the branch as dead. It is not dead: an explicit [] reaches it, and an empty slice is the only way to express that intent. Deleting the branch would silently change what [] means. Guarantees, each of which a consumer may rely on: - always a slice (a scalar `mainSections = 'posts'` is legal config and is coerced; `in` against a STRING set is a substring test, not membership); - every entry lowercased and trimmed, because Hugo reports .Section lowercased — `['Notes']` and `[' notes ']` would otherwise compile fine and then match nothing, silently costing a section its year pills; - an empty value is treated as unset, which is what a site with no main sections wants: the union in is-list-section.html still treats /posts/ and /archives/ as list sections regardless of this param, so [] could never have meant "no list sections". `isset` cannot distinguish the two here — it returns false for a configured ['posts'] as well as for []. Note the scope, per the measurement at the top: this covers an explicit [] only. Omitting the key never gets here, because Hugo supplies its own default. It exists because this param was read in five places, each with its own `default`, and the copies had already diverged in a way that shipped: the list page widened its set to the literal "archives"/"posts" names while the single templates gated on plain membership, so a post under /posts/ got year pills from one page and no breadcrumb or post-meta from the other. One definition, called from all of them. Measurements behind the above were taken on Hugo 0.146.0 and 0.166.0; re-run them before changing this partial rather than trusting the numbers in the PR history, which rot as Hugo moves. */ -}} {{- $mainSections := site.Params.mainSections -}} {{- if not $mainSections -}} {{- $mainSections = slice "archives" "posts" -}} {{- else if not (reflect.IsSlice $mainSections) -}} {{- $mainSections = slice $mainSections -}} {{- end -}} {{- $normalized := slice -}} {{- range $mainSections -}} {{- /* The cutset covers space, tab, CR and LF, not just " \t". Hugo's trim takes a set of CHARACTERS, so a value carrying a leading newline or a stray CR would keep it and then fail to match .Section, silently costing that section its year pills. A quoted YAML/TOML scalar usually arrives already stripped, so this is defensive rather than a known failure — but the stated intent of the trim is whitespace tolerance, and a cutset missing two of the four ASCII whitespace characters does not deliver it. printf "%v", not a bare lower/trim. A malformed config value -- an int, or a nested slice -- is coerced silently by those, producing a garbage entry like "1" or "[a b]" that matches no section, and this partial feeds 404.html, home.html, home.json and every single/section template, so one bad value degrades the whole site. An earlier version of this comment claimed the printf "makes the failure visible in the entry itself". That was not true and was not tested: no consumer validates or reports the entries, and html/json output shows the consumer, not this partial's return value. Measured with mainSections = [["a", "b"]]: the build SUCCEEDS, and /notes/ simply renders with no "browse all articles" link at all, because home.html:34 and 404.html:71 both do `index $mainSections 0` and hand it to site.GetPage "section", which finds nothing for "a b" or "[a b]". The failure is silent and its most visible symptom is a missing link, which is not obviously a config problem at all. So this stays a coercion, not a validation. Making it loud means a warnf or an errorf here, which would change build behaviour for sites that currently ship a broken-but-quiet config -- a bigger call than this branch makes on its own. Recorded instead, so the next reader knows the silent failure is a known consequence rather than a mystery. */ -}} {{- $normalized = $normalized | append (lower (trim (printf "%v" .) " \t\n\r")) -}} {{- end -}} {{- return $normalized -}}
